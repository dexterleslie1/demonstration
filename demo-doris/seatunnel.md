## 使用总结

>选用flink CDC替代此方案。

遇到问题：

- a字段会同步到b字段导致数据错乱。
- 布业系统中process数据同步全部表时同步失败，注释了某些表后才能够同步成功。

## 提醒

要指定Job Id才能使用之前的checkpoint重启，否则会重新全量同步一次数据。

```sh
# 固定 job id：有历史 checkpoint 时先 -r 恢复；首次部署或无可恢复位点时再用 --set-job-id 提交。
        JOB_ID=902337203685279362
        if ! ./bin/seatunnel.sh --config ./config/mysql_to_doris.conf -m local -r "$$JOB_ID" \
          -i "DORIS_ROOT_PASSWORD=${DORIS_ROOT_PASSWORD}" \
          -i "MYSQL_ROOT_PASSWORD=${MYSQL_ROOT_PASSWORD}"; then
          echo "[seatunnel-local] local restore failed (e.g. first run or no checkpoint), submitting with fixed job id..." >&2
          exec ./bin/seatunnel.sh --config ./config/mysql_to_doris.conf -m local \
            --set-job-id "$$JOB_ID" \
            -i "DORIS_ROOT_PASSWORD=${DORIS_ROOT_PASSWORD}" \
            -i "MYSQL_ROOT_PASSWORD=${MYSQL_ROOT_PASSWORD}"
        fi
```

数据同步不够实时（感觉延迟5秒左右，checkpoint.interval配置默认5秒左右），通过设置checkpoint.interval = 3000实现准实时同步感觉。

## SeaTunnel是什么呢？

SeaTunnel（全称 Apache SeaTunnel）是一个**非常易用、超高性能的分布式数据集成平台**，主要用于支持海量数据的实时与离线同步。

简单来说，它就像一个**数据的“超级搬运工”和“翻译官”**，能够帮助企业轻松地把数据从一个地方（比如 MySQL 数据库）稳定、高效地搬运到另一个地方（比如数据仓库、大数据平台或云存储）。

为了让你更全面地了解它，我为你总结了它的几个核心特点：

**1. 极其丰富的数据源支持（连接器生态）**
SeaTunnel 拥有超过 100 种连接器（Connector），几乎涵盖了市面上所有常见的数据源，包括各类关系型数据库（MySQL, PostgreSQL）、NoSQL 数据库（MongoDB, Redis）、消息队列（Kafka）、云存储（S3, OSS）以及各类 SaaS 服务等。无论是读取还是写入，它都能轻松打通。

**2. 批流一体，场景全覆盖**
它完美兼容各种复杂的同步场景，包括离线全量同步、离线增量同步、实时同步以及 CDC（变更数据捕获）等。这意味着你不需要为不同的同步需求去维护多套技术栈。

**3. 强大的多引擎支持与自研 Zeta 引擎**
*   **多引擎兼容**：SeaTunnel 可以基于你现有的技术组件，选择使用 Apache Flink 或 Apache Spark 作为底层执行引擎。
*   **自研 Zeta 引擎**：它内置了专为数据同步设计的默认引擎——**Zeta 引擎**。这个引擎最大的优势是**极其轻量**，不依赖 Hadoop、Zookeeper 等复杂的大数据组件，开箱即用，部署非常简单，同时在处理海量小表同步时能极大节省资源。

**4. 简单易用与可视化**
除了支持通过配置文件和编码来开发任务，SeaTunnel 还提供了 Web 界面（SeaTunnel Web）。你可以通过拖拽和类 SQL 语言来直观地设计数据同步任务，大大降低了数据开发工程师、分析师甚至科学家的使用门槛。

**5. 高可靠与高性能**
它每天可以稳定高效地同步数百亿甚至万亿级别的数据。同时，它支持分布式快照算法和完善的监控机制，能够保证数据在同步过程中不丢失、不重复（精确一次语义），让你对数据质量放心。

** 补充一个小知识：**
SeaTunnel 最初的名字叫 **Waterdrop**，在 2021 年正式更名为 SeaTunnel，并且是首个由国人主导的 Apache 顶级数据集成开源项目，目前在国内外数千家企业中都有落地应用。

如果你近期有跨数据库、跨平台的数据迁移或同步需求，SeaTunnel 绝对是一个非常值得尝试的工具。

## SeaTunnel Zeta引擎是什么呢？

SeaTunnel Zeta 引擎是 Apache SeaTunnel 社区**专门为数据集成和同步场景自研的新一代核心引擎**。

简单来说，如果说 SeaTunnel 是一个数据搬运工，那么 Zeta 引擎就是它自带的、专门为搬运数据而生的“专属跑车”。它旨在解决传统大数据引擎（如 Flink、Spark）在单纯做数据同步时存在的“资源消耗大、部署运维重、依赖组件多”等痛点。

为了让你更直观地了解它，我为你总结了 Zeta 引擎的几个核心亮点：

**1. 开箱即用，极其轻量**
Zeta 引擎最大的优势在于**不依赖** Zookeeper、Hadoop 等任何第三方大数据组件就能实现集群管理、高可用（HA）和作业容错。它内置了 Hazelcast 作为底层依赖来实现分布式内存网络和集群自治，下载解压后就能直接运行，大大降低了运维和部署的门槛。

**2. 性能强悍，资源占用极低**
Zeta 引擎在性能上做了大量深度优化，非常适合海量小表同步等场景：
*   **动态线程共享（Dynamic Thread Sharing）**：它不会简单粗暴地让一个任务占用一个线程，而是能动态感知并让多个轻量级任务共享同一个线程，极大减少了 CPU 资源的浪费。
*   **共享连接池与数据缓存**：当多个同步作业共用一个数据源时，Zeta 会自动复用 JDBC 连接，甚至将源端数据读取到共享 Cache 中，避免了对业务数据库造成过大的连接和读取压力。

**3. 细粒度的容错机制（Pipeline 级容错）**
传统的 Flink 引擎在遇到任务失败时，往往会触发整个作业的重启。而 Zeta 引擎采用了更聪明的 **Pipeline（管道）级容错**。
举个例子：如果你在一个任务中同步 A、B 两张表，当写入 B 表失败时，Zeta 只会重启负责 B 表的 Pipeline，而负责 A 表的 Pipeline 依然正常运行。这种设计在 CDC（变更数据捕获）等长周期同步场景中，能从根本上避免因为下游短暂故障导致上游数据库日志被清理而引发的数据丢失问题。

**4. 原生支持 CDC 与 Schema 演变**
Zeta 引擎原生支持全量、增量同步以及 CDC 场景，并且能够自动感知并同步源端的表结构变更（如增加列），这对于现代数据集成来说是非常实用的功能。

** 那么，SeaTunnel 的三大引擎（Zeta、Flink、Spark）该怎么选？**

官方给出的建议非常明确：
*   **如果你是新项目，或者没有现成的 Flink/Spark 运维体系**：强烈建议直接使用 **Zeta 引擎**。它的上手路径最短，运维负担最低，且在数据同步场景下性能和稳定性表现最佳。
*   **如果你已经拥有非常成熟的 Flink 或 Spark 集群**：为了复用现有的基础设施和运维经验，你可以选择让 SeaTunnel 跑在 Flink 或 Spark 引擎上。

## SeaTunnel checkpoint和savepoint是什么呢？

在 Apache SeaTunnel 中，**Checkpoint（检查点）**和 **Savepoint（保存点）**都是为了保障数据同步任务高可靠、不丢数据的核心容错机制。

你可以把它们都理解为作业运行时的“存档”或“快照”，记录了任务当前运行到了什么位置（比如读取到了 Kafka 的哪个 offset，或者 MySQL binlog 的哪个位置）。但两者的触发方式和主要用途有所不同：

**1. Checkpoint（检查点）：系统自动的“定时存档”**
*   **触发方式**：**全自动、周期性触发**。系统会按照你配置的时间间隔（例如每隔 10 秒或 60 秒）自动在后台执行。
*   **核心作用**：**故障自动恢复**。当作业因为网络抖动、节点宕机等意外情况突然失败时，SeaTunnel 会自动从最近一次成功的 Checkpoint 处无缝重启任务，从而保证数据不丢失、不重复（即精确一次语义）。
*   **存储位置**：通常会持久化到分布式存储中（如 HDFS、S3、OSS 等），以确保在集群任意节点故障后都能被读取到。

**2. Savepoint（保存点）：用户手动的“刻意存档”**
*   **触发方式**：**手动触发**。需要运维或开发人员通过命令行主动发起。
*   **核心作用**：**有计划的运维操作**。它主要用于作业的**计划内停止、升级、迁移或版本迭代**。当你需要暂停一个长期运行的任务，或者想升级 SeaTunnel 版本时，先打一个 Savepoint，就能确保任务在完美的状态下暂停。之后，你可以随时通过这个 Savepoint 让任务从暂停的地方继续运行。
*   **本质**：Savepoint 其实就是基于 Checkpoint 机制创建的一个特殊的全局状态镜像。

** 两者对比总结**

| 特性         | Checkpoint (检查点)                  | Savepoint (保存点)                 |
| :----------- | :----------------------------------- | :--------------------------------- |
| **触发方式** | 系统自动、定时触发                   | 用户手动触发                       |
| **主要目的** | 应对意外故障，实现自动容错恢复       | 应对计划内运维，如暂停、升级、迁移 |
| **生命周期** | 随作业运行自动管理，旧的会被定期清理 | 长期保留，直到用户手动删除         |

** 在 SeaTunnel 中如何使用？**

在 SeaTunnel Zeta 引擎中，你可以通过简单的命令行来操作 Savepoint：
*   **创建保存点（暂停任务）**：
    `./bin/seatunnel.sh -s {jobId}`
    执行后，作业会基于当前的 Checkpoint 机制生成一个 Savepoint 并结束任务。
*   **从保存点恢复（继续任务）**：
    `./bin/seatunnel.sh -c {jobConfig} -r {jobId}`
    使用 `-r` 参数，即可让作业从指定的 Savepoint 处恢复运行。

简单来说，**Checkpoint 是为了“保命”（防意外崩溃），Savepoint 是为了“存档”（方便随时读档继续）**。两者共同构成了 SeaTunnel 强大的数据一致性保障体系。

## SeaTunnel checkpoint的原理

Apache SeaTunnel 的 Checkpoint（检查点）机制是其实现数据“不丢失、不重复”（精确一次语义）的核心保障。它的底层原理基于经典的分布式快照算法——**Chandy-Lamport 算法**。

为了让你更直观地理解，我们可以把这个原理拆解为**“核心角色”、“工作流程”**和**“恢复机制”**三个部分来看：

### 1. 核心角色分工
在 SeaTunnel Zeta 引擎中，Checkpoint 的运作主要依赖以下几个核心组件协同工作：
*   **JobMaster**：作业的总指挥，负责监控作业状态。当发现任务失败需要恢复时，由它来主导恢复流程。
*   **CheckpointCoordinator（检查点协调器）**：这是 Checkpoint 的“中枢神经”。每个作业管道（Pipeline）都有一个独立的协调器，负责定期触发检查点、监控任务进度。
*   **Task（任务节点）**：包括 Source（读取）、Transform（转换）、Sink（写入）等具体干活的节点，它们负责在收到指令时保存自己的状态（比如当前读到了哪一行数据）。
*   **Checkpoint Barrier（检查点屏障）**：一种随着数据流一起流动的**特殊控制消息**，它像一道“栅栏”，用来划分不同检查点的数据边界。

### 2. Checkpoint 工作流程（以 Zeta 引擎为例）
Checkpoint 的生成是一个高度协同的过程，主要分为以下几步：

1.  **定时触发**：CheckpointCoordinator 按照预设的时间间隔（比如每 10 秒），自动生成一个全局唯一的 `checkpointId`，并启动一次新的检查点。
2.  **注入屏障（Barrier）**：协调器向数据源（Source）任务发送一个“检查点屏障”。这个屏障会像普通数据一样，沿着数据流管道向下游流动。
3.  **屏障对齐（Barrier Alignment）**：
    *   当某个任务（比如 Transform 或 Sink）有多个上游输入时，它需要**等待所有输入通道的屏障都到达**（即“对齐”），才能确保这一刻之前的数据都已经被处理完毕。
    *   对齐完成后，该任务会将自己的状态（例如 Kafka 的 offset、JDBC 的分片进度等）进行快照。
4.  **状态持久化**：各个任务将快照好的状态信息，异步地写入到外部的分布式存储中（如 HDFS、S3 或共享存储）。
5.  **确认完成（ACK）**：当所有任务都成功保存了状态并向协调器发送“确认（ACK）”后，协调器会认为本次 Checkpoint 成功，并将其记录为“已完成”。

### 3. 故障恢复原理（断点续传）
当作业因为节点宕机、网络异常等原因意外失败时，SeaTunnel 的恢复流程如下：

1.  **检测与加载**：JobMaster 检测到任务失败，会触发恢复流程。它会通知 CheckpointManager 去外部存储中查找该作业**最近一次成功的 Checkpoint**。
2.  **状态分发**：找到最新的 Checkpoint 后，协调器会将里面记录的各个任务的状态数据（比如“上次读到 MySQL 第 1000 行”）分发给新启动的任务节点。
3.  **重置与续跑**：任务节点加载这些状态，将 Source 的读取指针重置到故障前的位置（例如重置 Kafka Offset），然后从那个断点处继续处理数据，从而实现无缝续跑。

### 4. 性能优化与注意事项
为了减少 Checkpoint 对正常数据处理性能的影响，SeaTunnel 在原理设计上还做了很多优化：
*   **异步检查点**：任务线程只负责快速“冻结”状态快照，而将耗时的“序列化 + 上传到存储”的工作交给后台线程异步完成，最大程度降低对主数据流的阻塞。
*   **增量检查点（Incremental Checkpoint）**：在 Zeta 引擎中，支持只记录和上传**发生变化的状态数据**，而不是每次都上传全量状态。这大大减少了网络 I/O 和存储压力，使得高频检查点成为可能。
*   **状态轻量化**：最佳实践中，建议状态只保存“定位信息”（如游标、Offset），而不是把大量业务数据本身塞进状态里，这样能让 Checkpoint 更快、更稳。

** 特别提醒**：
Checkpoint 机制主要是为**流处理（Streaming）**或**CDC（变更数据捕获）**等长周期运行的作业设计的。如果你使用的是**批处理（Batch）**模式（一次性处理完有限数据集就结束），通常**不需要也不建议**配置 Checkpoint，否则可能会引起任务状态管理的混乱。

## SeaTunnel有哪些模式呢？

SeaTunnel 的“模式”可以从三个不同的维度来理解，分别是**部署模式**、**运行模式**和**引擎模式**。

### 1. 部署模式（针对 SeaTunnel Zeta 引擎）
这是指 SeaTunnel 自带的 Zeta 引擎在物理或集群层面的运行方式，主要分为三种：

*   **本地模式 (Local Mode)**：单进程运行，没有集群概念。主要用于开发阶段的配置快速验证、Connector 插件调试或小数据量测试。任务运行结束后进程会自动退出。
*   **混合集群模式 (Hybrid Cluster Mode)**：SeaTunnel 的 Master（主节点）和 Worker（工作节点）服务混合在同一个进程中。所有节点既可以运行作业，也能参与 Master 选举。适合中等规模的生产环境。
*   **分离集群模式 (Separated Cluster Mode)**：Master 服务和 Worker 服务完全分离，各自独立运行。**Master 节点**只负责作业调度、REST API 和任务提交；**Worker 节点**只负责任务的实际执行。这种模式架构最清晰，官方也**最推荐在生产环境使用**，因为可以避免大任务影响 Master 节点的稳定性。

### 2. 运行模式（作业执行方式）
这是指 SeaTunnel 处理数据时的逻辑方式，主要分为两种：

*   **批处理模式 (Batch Mode)**：适用于处理静态的、有界的数据集。例如，每天凌晨对 HDFS 中的历史数据进行全量清洗、聚合或离线同步。
*   **流处理模式 (Streaming Mode)**：适用于处理无界的、持续产生的实时数据。例如，实时消费 Kafka 中的消息并写入到 ClickHouse，常用于实时监控或在线分析场景。SeaTunnel 支持“批流一体”，同一套配置通过切换模式即可适应不同场景。

### 3. 引擎模式（底层执行引擎）
这是指 SeaTunnel 任务底层依赖的计算引擎，目前支持三种：

*   **SeaTunnel Engine (Zeta)**：SeaTunnel 自研的轻量级引擎，开箱即用，不依赖任何外部大数据组件，专为数据同步设计。
*   **Flink Engine**：基于 Apache Flink 提供强大的流批处理能力。如果你现有的技术栈已经深度依赖 Flink，可以选择此模式。
*   **Spark Engine**：基于 Apache Spark 运行，非常适合处理大规模的离线批处理任务。

** 简单总结：**
如果你刚开始接触，通常会使用 **Zeta 引擎** 的 **本地模式** 进行开发调试，作业逻辑可能是 **流处理** 或 **批处理**；当需要上线到生产环境时，则建议切换为 Zeta 引擎的 **分离集群模式** 以保证高可用和稳定性。

## SeaTunnel Job Id是什么呢？

在 Apache SeaTunnel 中，**Job Id（作业 ID）** 是系统为每一个提交的同步任务自动生成的**全局唯一标识符**。

你可以把它理解成任务在 SeaTunnel 集群中的“身份证号”。当你通过命令行或 REST API 提交一个作业后，SeaTunnel 会立即返回一个 Job Id，后续所有对该任务的监控、管理和运维操作，都必须依赖这个 ID。

具体来说，Job Id 主要有以下几个核心作用：

**1. 任务状态查询与监控**
你可以通过 Job Id 随时查看任务的运行状态（如 RUNNING、FINISHED、FAILED、CANCELED 等）以及详细的性能指标（如读取/写入的记录数、QPS、字节数等）。
*   **命令行方式**：`./bin/seatunnel.sh -j <jobId>`
*   **REST API 方式**：`GET /hazelcast/rest/maps/job-info/:jobId`

**2. 任务运维操作（暂停、恢复、取消）**
在任务运行过程中，所有的运维指令都需要指定 Job Id 来锁定目标作业：
*   **暂停任务**：`./bin/seatunnel.sh -s <jobId>`（基于 Checkpoint 暂停）
*   **恢复任务**：`./bin/seatunnel.sh -r <jobId> -c <配置文件>`（从断点续跑）
*   **取消任务**：`./bin/seatunnel.sh -can <jobId>`（强制停止并清除断点信息）

**3. 日志追踪与排查**
SeaTunnel 的日志系统支持结构化输出，Job Id 会被自动添加到日志的 MDC（映射诊断上下文）中。这意味着在排查问题时，你可以通过过滤 Job Id，快速从海量的集群日志中精准提取出属于该任务的所有日志信息，极大提升了排错效率。

**4. 区分不同的任务实例**
即使你使用完全相同的配置文件多次提交任务，SeaTunnel 也会为每一次提交生成全新的、互不干扰的 Job Id，从而确保各个任务实例能够独立运行和管理。

** 如何获取 Job Id？**
当你成功提交一个作业后，SeaTunnel 会直接在终端或 API 响应中返回 Job Id。例如，提交成功后通常会看到类似这样的返回信息：
```json
{"jobId":"964553575034257409","jobName":"st.example.template"}
```
拿到这个 `964553575034257409` 后，你就可以围绕它进行后续的所有操作了。

## SeaTunnel Job Id和checkpoint的关系

在 Apache SeaTunnel 中，**Job Id 和 Checkpoint 之间是“容器”与“内容”的绑定关系**。

简单来说，**Job Id 是 Checkpoint 的“专属身份证”和“存储索引”**。Checkpoint 数据必须依附于 Job Id 存在，系统通过 Job Id 才能精准地找到、管理和恢复特定任务的运行状态。

具体来看，它们的关系主要体现在以下三个核心层面：

**1. 存储索引关系（Job Id 是 Checkpoint 的“专属文件夹”）**
当 Checkpoint 被触发并持久化到外部存储（如 HDFS、S3 或共享文件系统）时，系统会自动以 Job Id 为名创建专属的存储目录。
*   例如，Checkpoint 数据通常会被保存在类似 `/seatunnel/checkpoint/{jobId}/` 的路径下。
*   这种设计确保了在同一个集群中，即使同时运行着成百上千个任务，每个任务的 Checkpoint 数据都能做到物理隔离，互不干扰。

**2. 恢复锚点关系（Job Id 是恢复任务的“导航坐标”）**
当任务因为故障宕机，或者你需要手动恢复一个暂停的任务时，Job Id 是找回 Checkpoint 的唯一凭证。
*   在恢复流程中，SeaTunnel 的 JobMaster 会根据你提供的 Job Id，去共享存储中扫描并定位该作业专属的检查点目录。
*   随后，系统会筛选出该 Job Id 下最新、最完整的那个 Checkpoint，加载其中的状态数据（如读取偏移量、算子状态等），从而让任务能够从“断点”处无缝续跑。

**3. 生命周期管理关系（Job Id 决定 Checkpoint 的“生死”）**
Checkpoint 的生成、清理和删除，完全受控于对应 Job Id 的生命周期：
*   **生成与暂停**：当你执行暂停命令（如 `./bin/seatunnel.sh -s {jobId}`）时，系统会为指定的 Job Id 触发一次保存点（Savepoint），本质上就是生成一个高质量的 Checkpoint。
*   **清理与取消**：系统会根据配置，定期清理某个 Job Id 下过期的历史 Checkpoint，以节省存储空间。特别需要注意的是，如果你执行了取消任务命令（`./bin/seatunnel.sh -can {jobId}`），系统不仅会停止作业，还会**强制删除该 Job Id 关联的所有 Checkpoint 信息**，这意味着该任务将无法再通过 `-r` 参数进行恢复。

** 总结**
你可以把 **Job Id** 想象成一个**“档案袋的编号”**，而 **Checkpoint** 就是档案袋里不断更新的**“工作进度记录”**。没有 Job Id，系统就找不到对应的档案袋；而没有 Checkpoint，就算找到了档案袋，里面也是空的，无法延续之前的工作进度。

## SeaTunnel设置Job Id

在 Apache SeaTunnel 中，设置 Job Id 主要有两种方式：一种是**在提交任务时主动指定**，另一种是**由系统自动生成**。

### 1. 主动指定自定义 Job Id
如果你希望为任务设置一个特定的 ID（例如为了配合外部的运维监控系统），可以在通过命令行提交作业时，使用 `--set-job-id` 参数来指定。

**命令示例：**
```bash
./bin/seatunnel.sh -c $SEATUNNEL_HOME/config/your_config.conf --set-job-id 10001 --async
```
这样，你提交的这个 SeaTunnel 作业的 ID 就会被固定为 `10001`。

### 2. 系统自动生成 Job Id（默认方式）
在绝大多数日常开发和生产场景中，我们通常不需要手动设置 Job Id。当你提交任务时，如果没有携带 `--set-job-id` 参数，SeaTunnel 集群会自动为该作业生成一个全局唯一的分布式 ID（通常是一串较长的数字）。

任务提交成功后，终端会直接打印出系统分配的这个 Job Id，例如：
```json
{"jobId":"964553575034257409","jobName":"st.example.template"}
```
你只需要记录下这个 ID，就可以用于后续的监控、暂停或恢复操作了。

### 补充说明：Job Id 与 Job Name 的区别
在实际使用中，很多人容易把 Job Id 和 Job Name 搞混，这里简单区分一下：
*   **Job Id**：是任务的**唯一身份标识**，用于系统底层的精准定位、状态恢复和存储索引。
*   **Job Name**：是任务的**显示名称**，主要用于在 Web 界面或日志中方便人类识别。你可以通过 `-n` 或 `--name` 参数来设置，如果不设置，默认名称通常是 `SeaTunnel`。

**设置 Job Name 的示例：**
```bash
./bin/seatunnel.sh -c $SEATUNNEL_HOME/config/your_config.conf -n "MySQL到Oracle同步任务" --async
```

**小建议**：除非你有非常明确的跨系统对接需求，否则建议直接使用系统自动生成的 Job Id，这样可以完全避免手动指定 ID 可能带来的重复或冲突风险。
